1. Websites can reach local agent tools without credentials

Local MCP requests bypass authentication, CORS accepts arbitrary HTTP and HTTPS origins, and the MCP handler has no Origin protection configured. A request with Origin: https://review.invalid successfully initialized, listed 58 tools and invoked the harmless agent-options tool in one JSON-RPC batch. Batching avoids needing to read or resend the MCP session header.

A webpage that can reach localhost can therefore reach sensitive agent tools. Actual browser exploitation depends on the browser's local-network restrictions; this audit verified server acceptance and CORS preflight responses, without running an attack page. Email and other consequential tools were inspected in source and were not invoked.

Require agent credentials at the MCP boundary and enforce explicit trusted browser origins. Remove IP-based authentication exemptions. An origin allowlist alone does not authenticate local programs.

2. The tunnel bypasses extension-bridge authentication

The tunnel forwards requests from localhost. The extension exemption accepts any syntactically valid extension Origin, which an Internet client can supply. A public request without credentials returned 401; adding a fabricated extension Origin reached the WebSocket upgrader and returned 400 for missing upgrade headers.

The bridge accepts a self-declared protocol hello and replaces its previous client. This permits bridge impersonation and interception of extension-directed browser actions when Extension mode is used. Current settings select Desktop mode, so a takeover of the active side browser is not established. The audit deliberately did not complete a bridge hello or replace a client.

Authenticate bridge clients with a dedicated credential and remove the localhost-plus-Origin exemption. Restrict public ingress to the client API surfaces that need it.

3. Every approved device can obtain permanent enrollment authority

The connection-link endpoint returns the shared root key to an ordinary approved device. Possession of that key permits immediate approved registration of another device. The root key remains valid when an individual device is revoked.

An isolated server with the real HTTP handlers, device service and SQLite adapter confirmed both steps: device-token access to the root-bearing link returned 200, and root-key enrollment returned 200 with an approved device and token. A compromised phone can retain enrollment authority beyond its device's revocation.

Keep the root key local to bootstrap and recovery. Replace root-bearing QR links with expiring, single-use enrollment invitations, and make recovery-key rotation explicit. Existing root links should be treated as administrator credentials.

4. Revocation leaves an existing terminal operational

Device authentication runs before WebSocket upgrade. Terminal input then executes without another device check, and revocation does not cancel the device's open connections.

An isolated production-route probe opened a terminal, revoked its device and verified that fresh HTTP requests returned 401. The already-open terminal then successfully executed a command that wrote a marker inside the isolated audit directory. The hidden terminal and server were closed afterward.

Associate long-lived streams with their authenticated device and cancel them when it is revoked. Apply this ownership contract to terminals, browser/computer streams and event subscriptions. Revocation should end access without requiring a server restart.

Medium
5. URLs carry durable credentials

Root links contain ?key=. Event streams, browser/computer/terminal sockets and embedded files use device tokens in URL queries. Pairing polling sends ?secret=, and that same secret becomes the approved device's persistent bearer token. Expiry applies to pending pairing, while approved device tokens have no expiry check.

URL capture in proxy logs, copied links or diagnostics can therefore capture reusable access. This audit establishes the exposure paths, not an actual leak. Native iOS socket requests already support an Authorization header but also append the token to the URL.

Use headers where supported. Exchange short-lived, single-use tickets for browser transports that cannot set headers, and exchange pairing proof for a distinct device credential. Redact credentials from URLs and diagnostic output.

Medium
6. Connected-account credentials are stored as plain JSON

OAuth access tokens, refresh tokens and client secrets are serialized directly into SQLite. The running database and WAL have mode 0644; the Jaz directory has mode 0755. The home directory has mode 0750 with group staff, so other-user access still depends on ancestor permissions and ACLs. Six OAuth-token rows exist; no token values were printed.

A copied database or a process able to read it can obtain connected-account credentials. Desktop device bearer tokens also reside in renderer localStorage. The iOS client uses Keychain, and the server root-key file is correctly mode 0600.

Use a private runtime directory and restrictive database/WAL permissions. Protect reusable OAuth secrets with the platform credential store or an external secret key, and move desktop credentials behind the main-process credential boundary. Backups need the same protection.

Medium
7. The backend also listens on every network interface

The running server listens on *:5299, matching the default :5299 listen address. The phone tunnel only needs a loopback origin, so the wider listener adds a separate LAN-facing HTTP surface. Actual reachability from another device depends on the Mac firewall and network.

The clients also default a scheme-less address to HTTP. Your configured phone tunnel uses HTTPS; this finding concerns the additional direct listener and other connection choices.

For a same-computer tunnel deployment, bind the backend explicitly to loopback. Require HTTPS for ordinary remote connections, with an explicit local development exception where needed. Keep intentional LAN deployments separately configured.
