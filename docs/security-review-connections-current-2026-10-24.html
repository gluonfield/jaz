The tested public routes enforce authentication. Four remaining defects concern pairing and optional manual MCP credentials. Approved devices also have broad administrative authority.

Remaining defects

PriorityFinding, evidence and correction
Medium
1. Old pairing approval survives revocation and re-enrollment

An approved pairing proof that has never been redeemed remains usable until its original ten-minute expiry. After revoking and re-enrolling the same device, that old proof can obtain a new valid bearer credential and invalidate the freshly issued credential.

Reproduced with the real device service and SQLite adapter: approve without claiming → revoke → re-enroll the same identity → redeem the old proof. The old proof succeeded and the fresh bearer stopped authenticating. This requires a previously approved, unclaimed proof and reapproval of the same identity inside ten minutes; it does not let arbitrary pending requests bypass approval.

Invalidate every outstanding pairing authorization atomically whenever a device is revoked or its credential is replaced. Preserve only the pairing currently being claimed.

Medium
2. Anonymous pairing can overwrite a known approved device’s identity display

When the target’s public key and derived device ID are known, an unauthenticated pairing request can change that approved device’s name, kind, platform and other profile fields. The endpoint verifies the public-key hash but requires no private-key proof. The approved status and existing bearer remain valid.

Reproduced through the production HTTP router and handler against an isolated database: an anonymous request returned 202 and changed an approved phone into the supplied desktop name/type. This is an integrity and approval-confusion defect; this test did not obtain access without approval or discover real device keys.

Keep proposed identity/profile data on the pairing request. Update the canonical device only after approval and successful credential exchange. An unauthenticated request must not edit an approved record.

Medium
3. Public pairing admission has no application-level bound

The unauthenticated pairing endpoint persists devices and requests without a rate limit, pending-request cap or periodic retention policy in this path. Listing retrieves all records; the UI treats every stored pending status as pending, including requests whose deadline has elapsed without another operation updating their status.

A bounded isolated run accepted all 24 successive anonymous requests with distinct identities and persisted all 24. Live testing used invalid input only and returned the origin’s validation error through the tunnel. No live flood or availability test was performed; Cloudflare account-wide WAF/rate-limit policy was not audited.

Bound public enrollment admission and retention in the device service/storage boundary. Prefer a short, owner-opened enrollment window or invitation for unsolicited pairing; add edge rate limiting as another layer.

Medium, conditional
4. Manually entered MCP bearer tokens and literal headers remain plaintext

The OAuth token store is encrypted, but the manual MCP configuration path writes bearer tokens and literal header values directly into SQLite.

A dummy inactive server saved through CreateMCPServer had its dummy bearer and X-Api-Key header readable verbatim from the database. No provider was contacted. The live database currently contains zero manual MCP records, so this path exposed no current credential in this review.

Route secret-bearing MCP fields through the existing encrypted credential store. Keep ordinary configuration separate and redact secret values from read DTOs.

backend/internal/storage/sqlite/mcp.go:55

Device authority

Every approved device can use privileged APIs and create an invitation that immediately approves another device. In an isolated run, a phone enrolled a successor; revoking the phone left the successor active. This follows the current trust model and is distinct from the pairing defects above.

Treat a stolen phone bearer as computer compromise: terminal execution, connected-account actions and enrollment authority share this boundary. Separate device administration from ordinary client access, with owner approval for enrollment. Existing descendants require their own revocation.
